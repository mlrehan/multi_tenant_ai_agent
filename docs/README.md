**Phase 5 (authentication module) is code, not a doc** — it lives in `src/iam_platform/` (`core`, `domain/identity`, `application/identity`, `infrastructure`, `api`), `alembic/versions/`, and `tests/`. See [../CLAUDE.md](../CLAUDE.md)'s "Phase 5 — what's built" section for scope, verification status, and how to run it locally. The 18/10-schema docs above were amended in place during Phase 5 where implementation surfaced a real correction (`sessions.mfa_verified` column, the `server_default` string-vs-function pitfall, the Unit-of-Work rollback-on-raise pitfall) — those docs are kept as ground truth, not left to drift from the code.

**Phase 6 (platform and tenant authorization module) is also code, not a doc** — it lives in `src/iam_platform/` (`domain/{tenancy,platform_authz,tenant_authz}`, `application/{tenancy,platform_authz,tenant_authz,impersonation}`, `infrastructure/db/{models,repositories}`, `api/{platform,tenants,memberships,rbac,impersonation}`), `alembic/versions/c1178e6fb886_platform_tenancy_and_tenant_.py`, and `tests/`. See [../CLAUDE.md](../CLAUDE.md)'s "Phase 6 — what's built" section for scope, verification status, and the three non-obvious findings from implementation. [18-schema-rls-and-migrations.md](18-schema-rls-and-migrations.md) was amended twice during Phase 6 (the pooled-connection `NULLIF` fix, the `tenants`-table RLS gap, and the `CREATE POLICY` one-command-per-policy syntax error) and [14-schema-tenant-authorization.md](14-schema-tenant-authorization.md)'s `role_hierarchy`/`tenant_role_permissions` tables gained a denormalized `tenant_id` column beyond the original design — both kept as ground truth, not left to drift from the code.

**Phase 7 (APIs and AI-resource policies) is also code, not a doc** — it lives in `src/iam_platform/` (`domain/ai_resources`, `application/ai_resources`, `infrastructure/{storage,vector,queue,security/encryption.py}`, `api/v1/assistants`), `alembic/versions/79c1357c7aeb_ai_resources_schema.py`, and `tests/`. See [../CLAUDE.md](../CLAUDE.md)'s "Phase 7 — what's built" section for scope, the two structural guarantees it enforces (server-derived vector namespaces/storage paths, and the provider-secret boundary), and the two schema corrections implementation surfaced. [16-schema-ai-resources.md](16-schema-ai-resources.md) is amended below with both corrections rather than left to drift.

**Phase 8 (tests and security validation) is code, not a doc** — it lives in `tests/security/` (one negative test per mandatory threat-model scenario, plus an append-only audit guard), `tests/api/test_ai_resource_authorization.py`, `src/iam_platform/domain/impersonation/`, and `alembic/versions/937a69c41b65_append_only_audit_tables.py`. The phase found and fixed **two defenses the design specified but the code never implemented** (impersonation privilege scope, and append-only audit grants) — see [../CLAUDE.md](../CLAUDE.md)'s "Phase 8 — what's built". [03-threat-model.md](03-threat-model.md)'s scenario table now carries a "Proven by" column mapping each defense to the test that holds it, including honest ⚠ markers where coverage is partial.

**Phase 9 (deployment and operations)** is both code *and* a doc — [22-deployment-and-operations.md](22-deployment-and-operations.md) is the runbook (topology, expand/contract migrations, secrets and key rotation, health-endpoint semantics, observability, scaling arithmetic, failure modes, pre-deploy checklist, known gaps), alongside `Dockerfile`, `.dockerignore`, `docker-compose.prod.yml`, and `src/iam_platform/{asgi.py, infrastructure/ops, infrastructure/secrets, api/middleware/{rate_limit,metrics}.py}`. Like Phase 8, it found **three defenses that were designed but inert** — unresolved `secret://` references (which meant the service could not have started correctly in production), a `/readyz` stub that could never fail, and resources that were never disposed on shutdown. See [../CLAUDE.md](../CLAUDE.md)'s "Phase 9 — what's built".

---

**The admin console (`frontend/`) is code, not a doc** — a Next.js 16 + TypeScript + Tailwind + shadcn/ui web console covering auth, platform administration, tenant RBAC, and the AI-resource surfaces. See [../frontend/README.md](../frontend/README.md) for its architecture (notably the BFF proxy that keeps tokens out of the browser entirely) and [../CLAUDE.md](../CLAUDE.md)'s "Admin console — what's built" for the read endpoints it required and the three bugs building it uncovered — including a `RevokePlatformRole` use case that had **no authorization check at all**, and a login crash on unknown email addresses whose root cause also meant the anti-enumeration timing mitigation wasn't working.

---

**All 9 original delivery phases are complete.** The docs above are the living spec; where implementation contradicted a design doc, the doc was amended in place rather than left to drift, so they describe the system as built. Start at [09-roadmap.md](09-roadmap.md) for phase-by-phase status and [22-deployment-and-operations.md](22-deployment-and-operations.md#known-gaps) for what remains deliberately unbuilt.

**Phases 10–14 are complete** — see [24-knowledge-base-ingestion-and-rag.md](24-knowledge-base-ingestion-and-rag.md). The pipeline runs end to end: an uploaded file or crawled site becomes searchable, and an embeddable widget answers a stranger's question on a third-party page with grounded, cited, streamed answers. That document also records the performance pass that followed — a PDF text-layer fast path (1,351× on a text-native document) and a bound on reasoning latency.

**For non-developers**, start with [25-platform-admin-guide.md](25-platform-admin-guide.md) (running the service) or [26-tenant-admin-guide.md](26-tenant-admin-guide.md) (running one customer organisation) rather than anything above.
